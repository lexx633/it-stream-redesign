# Code Review Checklist — it-stream-redesign (стек: статический HTML/JS + PHP на шаред-хостинге)

> **v1.0 — 2026-08-11.** Копия и адаптация `_rxapp/docs/code-review-checklist.md` (v2.0) под
> реальный стек этого проекта. Исходник заточен под Node/TS/Remix/Prisma/Shopify — большая
> часть пунктов сюда не переносится физически (нет CI, нет БД, нет npm, нет фреймворка).
> Оставлено и переписано то, что применимо к: пяти статичным HTML-страницам с общим CSS/JS,
> двум JSON-моделируемым страницам (`index.html`, `blog.html`/`blog-post.html` через
> `content.json`), визуальному редактору `admin.html` (contenteditable + iframe), и пяти
> PHP-эндпоинтам (`save.php`, `upload-image.php`, `list-uploads.php`, `send-lead.php`,
> `_setup_pass.php`) на обычном Apache-хостинге (ihc.ru, `mod_rewrite`, без shell-доступа
> для деплоя иного, чем SSH/`plink`/`pscp`).
>
> **Маркировка:** 🤖 = можно проверить командой (grep/php -l/curl) без чтения глазами.
> 👀 = только чтением кода/глазами.

## §0. Три уровня прохода

| Уровень      | Когда                                                      | Что проходить                          |
| ------------ | ----------------------------------------------------------- | --------------------------------------- |
| **Smoke**    | текст, вёрстка, правка одной страницы без нового PHP-кода   | §5 экспресс-скан + 🤖-пункты            |
| **Standard** | обычная задача (новая страница, новое поле в content.json)  | Smoke + §§1–4 целиком                   |
| **Deep**     | новый PHP-эндпоинт, загрузка файлов, деплой, пароль/секреты | Standard + §6 целиком + деплой-протокол |

## 1. Security (первым)

- [ ] 🤖 **Секреты в diff.** Пароль/токен/хэш не появляется в чат/коммите. Значения из `.env`
      (`SSH_L`, `SSH_P`) — только имя переменной в чате, не значение. `git diff --cached`
      перед коммитом — нет `.env`, `.pass`, `*.bak`, дампов `_work`/`_data`.
- [ ] 👀 **Пароль эндпоинтов — только `password_verify()` против хэша вне веб-корня**
      (`~/data/.it-win-admin.pass`, не в `www/`). Plaintext пароль нигде не логируется и не
      уходит в ответ. Новый PHP-эндпоинт с записью на диск обязан повторить эту проверку —
      не полагаться на «пришёл из admin.html, значит свой».
- [ ] 👀 **Whitelist на запись файлов.** Любой PHP, пишущий на диск по имени из запроса
      (`page`, `kind`, `file`) — сверяет имя со статическим массивом (`$ALLOWED_PAGES` в
      `save.php`), не строит путь напрямую из пользовательского ввода. Имена загружаемых
      файлов — генерируются на сервере (timestamp+random), не берутся из `$_FILES['file']['name']`.
- [ ] 👀 **Тип файла — по содержимому (`finfo`), не по расширению/`Content-Type` из запроса.**
      `upload-image.php` уже так делает — новый загрузочный эндпоинт обязан повторить.
      SVG — сознательно не в списке разрешённых (может нести `<script>`).
- [ ] 👀 **Размер запроса ограничен.** `php://input` читается с проверкой `strlen()` (см.
      `save.php` — 4 МБ), загрузка файла — с проверкой `$_FILES[...]['size']` (2 МБ). Новый
      эндпоинт без лимита = вектор DoS на шаред-хостинге с общими ресурсами.
- [ ] 👀 **XSS в HTML-полях `content.json`.** `data-cms-html`/`innerHTML =` — осознанный
      trusted-HTML контур (правит только владелец пароля через админку), не user input с
      публичного сайта. Публичные формы (`send-lead.php` и т.п.) никогда не попадают в
      `content.json` напрямую и не рендерятся `innerHTML` — только текстом в письме.
- [ ] 👀 **Публичные формы (`send-lead.php`) — только текстовые письма, без HTML-инъекции
      в заголовки.** `\r`/`\n` из полей вычищены (`clean_line()`) до попадания в `Subject`/
      `From`/тело — иначе email header injection. Новое поле формы — та же очистка.
- [ ] 👀 **Атомарная запись + бэкап перед перезаписью.** `save.php` — `tmp+rename`, снимок
      в `~/data/backups` перед каждой правкой. Новый эндпоинт, правящий существующий файл
      (не только создающий новый) — обязан то же самое, иначе одна параллельная правка
      Owner'а через живую админку молча теряется (см. `feedback_itwin_deploy_before_pull`
      в памяти — уже случалось).
- [ ] 👀 **`.htaccess` — общий на домен, не только на этот проект.** На `it-win.ru` в одном
      файле уживаются правила this-репозитория и правила `profclinic-arbat` (другой git-репозиторий,
      правится не отсюда). Перед любой правкой `.htaccess` — скачать живой файл и сверить,
      не перетереть чужие правила (см. §6).
- [ ] 👀 **Одноразовые setup-скрипты (`_setup_pass.php`) не переиспользуемы во вред.**
      Скрипт no-op'ает, если пароль уже стоит (`ALREADY_SET`) — не перезаписывает тихо
      существующий хэш. Если такой скрипт больше не нужен — не оставлять в веб-корне
      бессрочно, вынести за пределы `www/` или удалить после использования.

## 2. Logic & Reliability

- [ ] 👀 **Пути к ресурсам — абсолютные, не относительные, на любой странице с непредсказуемой
      глубиной маршрута.** Грабли этой сессии: `fetch('content.json')` на `/blog/<slug>`
      (два сегмента пути) резолвился в `/blog/content.json` → 500. Всегда `fetch('/content.json')`
      на страницах, доступных не только с корня. Тот же принцип — для `href`/`src` без
      `data-cms-href`/абсолютного `/`.
- [ ] 👀 **`mod_rewrite` — новое правило проверено в живом порядке правил, не только регуляркой
      «на бумаге».** Порядок в `.htaccess` важен (redirect HTTPS → спец-каталоги → чистые
      URL → generic catch-all). Новое правило для конкретного пути — вставлять ДО общих
      catch-all правил, иначе не долетает.
- [ ] 👀 **`fetch().then()` цепочки — есть `.catch()` или он не нужен по контракту.** В этом
      проекте нет `await`/async-функций верхнего уровня — все загрузки данных через промисы;
      непойманная ошибка = молчаливо отвалившийся рендер без сообщения пользователю
      (`.catch(function(){})` — осознанный fallback на дефолтные значения из HTML, не забытый).
- [ ] 👀 **`window.CMS`/`window.__cmsReady`-контракт соблюдён на каждой JSON-странице.**
      `admin.html` ждёт `window.CMS.render`/`revealAll`/`__cmsReady` перед тем как включить
      редактирование — новая JSON-страница без этого контракта не будет редактируемой
      (зависнет молча на 8 секунд опроса, `installEditor` не вызовется).
- [ ] 👀 **Пустые состояния предусмотрены.** Фильтр по тегу без совпадений, `blog.posts`
      пуст, `content.json` не загрузился (`catch`) — страница не падает в белый экран, есть
      текст-заглушка (`.empty-note`, `.not-found`).
- [ ] 👀 **HTTP-статусы PHP-ответов семантичны.** `fail()`-хелпер везде выставляет реальный
      код (`400`/`401`/`413`/`500`), не `200` с `ok:false` в теле молча.

## 3. Performance & Resources

- [ ] 👀 **Загрузка изображений — лимит размера + сжатие/формат.** `upload-image.php`
      (2 МБ потолок, только png/jpeg/webp, без SVG) — новый загрузочный путь обязан то же.
- [ ] 👀 **`content.json` не раздувается бесконтрольно.** Каждая новая статья блога/отзыв/
      кейс — реальный контент, не тестовые заглушки, забытые в проде. Файл читается целиком
      на каждой JSON-странице при каждой загрузке — счёт на сотни, не тысячи записей.
- [ ] 👀 **Раздутые raw-страницы.** Пять статичных страниц дублируют один и тот же
      CSS/шапку/подвал ~900 строк каждая — известный компромисс архитектуры (см.
      `docs/decisions.md` Р-65), не повод копировать дубль в шестой раз бездумно: сначала
      смотреть, нельзя ли вынести общее в `content.json`-модель, как сделано для блога.

## 4. Code Quality

- [ ] 👀 **Консистентность паттернов.** Новый JSON-рендер — `esc()`/`escAttr()` на каждый
      вывод пользовательского/CMS-текста в HTML/атрибут (не голая конкатенация строки).
      Новое поле в `content.json` — camelCase/dot-path в общем стиле остальных ключей
      (`section.field`, не `section_field`).
- [ ] 👀 **Комментарии объясняют «почему», не «что».** В PHP/JS этого проекта — короткие
      комментарии на неочевидных местах (whitelist, атомарная запись, абсолютный fetch)
      уже норма, держать её.
- [ ] 👀 **Мёртвый код убран.** Правка, отменяющая старый UI-элемент (пример этой сессии:
      `#pageSel`/`#vars` → дерево «Страницы») должна убрать и его CSS/JS-обвязку, не только
      разметку — иначе в файле копится нерабочий след старого решения.
- [ ] 👀 **Размер файла.** HTML-файлы этого проекта уже большие (embedded CSS+JS) — это
      осознанный компромисс архитектуры (одностраничники без сборки), не повод добавлять
      сверху ещё один независимый слой стилей/скриптов вместо переиспользования существующего.

## 5. Verification (замена автотестов — их в проекте нет)

- [ ] 👀 **Каждая новая страница/фича — открыта живьём в браузере**, не только просмотрена
      как diff. `preview_start`/локальный `http.server` — минимум для страниц без PHP.
      PHP-эндпоинты (пароль, запись на диск) физически нельзя проверить без реального сервера
      (PHP тут не поднять локально штатными средствами) — проверяются после деплоя на живом
      `it-win.ru`, не выдаются за «протестировано» до этого.
- [ ] 🤖 **`content.json` — валидный JSON** (`python -c "import json; json.load(open(...))"`)
      перед каждым коммитом, трогающим этот файл руками.
- [ ] 👀 **После деплоя — открыть реальный URL и прочитать консоль браузера** (не только
      «файл залился без ошибки pscp» — HTTP 200 на `pscp`/`curl` не доказывает, что страница
      реально работает, см. живой баг с `/blog/<slug>` этой сессии, пойманный только открытием
      страницы в браузере после первой заливки).

## 6. Правила из граблей этого проекта (it-win.ru / it-stream-redesign)

### 6.1. Деплой — ВСЕГДА pull-diff-push, никогда «залил и забыл»

- **Перед каждой заливкой:** скачать живую версию каждого затрагиваемого файла (`pscp` вниз),
  сравнить с `git HEAD` (`diff --strip-trailing-cr` — хостинг может отдавать CRLF, это не
  реальная правка). Если живой файл разошёлся с git — **не значит «Owner ошибся»**: может
  быть законная правка из другой сессии/дорожки (пример этой сессии — `.htaccess` с
  HTTPS-force и `/profclinic-arbat` правилами от соседнего проекта). Смёржить вручную,
  не перезаписывать слепо.
- **После каждой заливки:** открыть реальный URL в браузере, не полагаться на код `200` от
  `pscp`/`curl -I` — он подтверждает только «файл принят SFTP», не «страница работает»
  (относительные пути, JS-ошибки, mod_rewrite-конфликты видны только в браузере).
- `plink`/`pscp` в `-batch` без `-hostkey` виснут на первом подключении — фингерпринт
  фиксировать в памяти проекта на будущее, не гадать заново.
- `.env`: `SSH_L` уже содержит `user@host` целиком — не приписывать `$SSH_L@host`.

### 6.2. `.htaccess` — общий домен-ресурс, не файл одного проекта

- На `it-win.ru` уживаются правила `it-stream-redesign` (этот репозиторий) и правила
  `profclinic-arbat` (демо-каталог другого репозитория, живёт вне git этого проекта).
  Правка `.htaccess` из этой сессии обязана: (1) скачать живой файл, (2) вставить своё
  правило в правильное место относительно уже стоящих чужих правил, (3) залить обратно
  весь файл целиком (Apache не умеет частичный `.htaccess`).

### 6.3. `content.json` — единый источник, не плодить copy-paste полей

- Новое поле для главной/блога — сначала проверить, нет ли уже подходящего в `VAR_GROUPS`
  (`admin.html`) или в существующей секции `content.json`, прежде чем заводить новый ключ.
- Массивы объектов (`blog.posts`, `reviews.items`, `faq.items`) — общий паттерн: рендер через
  `TPL[...]`/`data-cms-list`, шаблон нового элемента — через `ITEM_TPL` в `admin.html`. Не
  городить отдельный ad-hoc рендер для нового списка, если подходит существующий паттерн.

### 6.4. Относительные URL — только на страницах с фиксированной глубиной маршрута

- `index.html`, статичные `/skud` и т.п. — глубина маршрута всегда 1 сегмент, относительный
  `fetch('content.json')` резолвится верно случайно, не по гарантии. Любая новая страница,
  доступная по маршруту с переменной глубиной (`/blog/<slug>`, потенциально будущие
  вложенные разделы) — **только абсолютные пути** (`/content.json`, `/uploads/...`).

### 6.5. admin.html — редактируемость страницы не сама собой разумеется

- JSON-страница становится редактируемой в `admin.html` только если: (1) зарегистрирована
  в `PAGES` с `json:true`; (2) выставляет `window.CMS = {data, render, revealAll}` и
  `window.__cmsReady`/`cms:ready` по контракту `index.html`; (3) элементы, которые должны
  редактироваться текстом — с `data-cms`/`data-cms-html`; списки — с `data-cms-list` на
  контейнере. Забыть любой из трёх пунктов — страница откроется в iframe, но редактор
  внутри не включится (либо молча, либо после 8с таймаута).
- raw-страницы (json:false) — редактируемый текст только через `RAW_SEL` в `admin.html`;
  новый визуальный элемент, который должен быть contenteditable — добавить его селектор
  туда явно, иначе клик по нему просто ничего не делает.

## 7. Быстрый скан антипаттернов (30 секунд, применимо к любому стеку)

- [ ] Оборванный код / `TODO: реализовать` / недописанные ветки — в проде такого нет.
- [ ] Комментарий врёт про то, что делает код рядом (правили логику — не обновили комментарий).
- [ ] Переусложнение — for-loop на 3 итерации не нужно оборачивать в générique-абстракцию.
- [ ] Отладочные `console.log`/`var_dump`/`echo` не в проде.
- [ ] Дублирование одной и той же проверки в двух PHP-эндпоинтах — вынести общий include,
      если появится третий похожий (сейчас 4 эндпоинта дублируют проверку пароля — терпимо,
      пятый-шестой уже повод вынести).

## 8. Матрица критичности

| Уровень          | Область                                                                                          | Действие                        |
| ---------------- | -------------------------------------------------------------------------------------------------- | -------------------------------- |
| 🔴 Critical      | Пароль/хэш утёк в чат или коммит; whitelist на запись файла отсутствует/обойдён; XSS с публичной формы в `content.json`/письмо; `.htaccess` залит поверх чужих правил | Блокирует деплой. Чинить немедленно. |
| 🟠 Important     | Относительный путь на странице с переменной глубиной; забытый `window.CMS`-контракт; нет лимита размера на новом эндпоинте; отсутствие бэкапа перед перезаписью | Чинить в рамках этой же задачи. |
| 🟢 Nice to have  | Стиль, именование, комментарии, косметика                                                        | Рекомендательно.                 |
